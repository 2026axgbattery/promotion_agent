# MVP 구현 계획서 — 프로모션 효과 시뮬레이션 에이전트

- **근거 문서**: `02_PRD.md`(5절 기능 목록의 MVP 표, 6.1~6.4·6.8절 상세 요구사항, 7절 데이터 모델, 8절 엣지 케이스, 9절 성공 지표), `08_기술스택.md`(Streamlit/pandas/openpyxl/DuckDB 확정 스택)
- **전제**: 3일 집체 개발(PBL) 일정이며, 실제 애플리케이션 코드는 아직 없다(기획 단계). 본 계획서는 코드 작성을 시작하기 전 범위·순서·완료 기준을 먼저 고정하기 위한 문서다.

**(수정, 사용자 확인 — Day 1 완료 후 반영)** 이 계획서 작성 이후 실제 월 마감 워크북(`sample04.xlsx`류)을 검토한 결과, 프로모션ID·대리점등급은 실제로 존재하지 않는 개념임이 확인되어 삭제했다(`02_PRD.md` 10절). 아래 "포함(MVP)" 7번 "기준 미등록 경고"와 "완료 기준과 무관하게 처리해야 하는 엣지 케이스"의 프로모션ID 관련 항목은 더 이상 적용되지 않는다. 또한 실제 데이터는 대리점 단위로 이미 계산된 DC/프로모션 지원금액을 담고 있어(산식으로 새로 계산하는 구조가 아님), Day 2는 "산식 매칭 엔진" 대신 `app/workbook_ingest.py`의 다중 시트 인입·배분 로직을 기준으로 진행한다.

## 배경/동기
`02_PRD.md`는 사용자가 제공한 과제 등록 정보에 맞춰 MVP 범위를 "엑셀 업로드 → DC율 반영 매출·제품군 합산 판정·지원금액 자동계산 → 영업이익율·매출증감율 표시"까지로 재정렬했고(편차 원인 구분·효과성 평가·그룹별 조회·이력 조회 UI·프로모션 간 비교 등은 "최종 결과물" 단계로 이연), 기술 스택도 Streamlit+pandas+openpyxl+DuckDB로 확정했다. 그러나 아직 이 범위를 실제로 "어떤 순서로, 어떤 화면 구성으로, 무엇을 완료 기준으로 삼아" 만들지는 문서화되어 있지 않다. 이 계획서는 그 간극을 메운다.

## 범위

### 포함 (MVP)
`02_PRD.md` 5절 MVP 표 그대로:
1. 실적 파일 업로드 (6.1)
2. 프로모션 기준 마스터 업로드 (6.2)
3. DC율 반영 매출 확인
4. 제품군 합산 판정
5. 지원단가·지원금액 산출 — 산식유형 4종(구간별단가-절대수량/구간별단가-대리점별상대/무상증정(10+1)/품목별고정단가) + 연동형, 복수 프로모션 동시 매칭, DC/프로모션 지원금액 분리 (6.3)
6. 영업이익율·매출증감율 병렬 표시 (6.4)
7. ~~기준 미등록 경고~~ **(삭제, 사용자 확인)** — 프로모션ID 개념이 없어 더 이상 적용되지 않는다.
8. 분석 결과 DB 저장 — DuckDB에 기준연월 키로 저장(쓰기), 재분석 시 덮어쓰기 (6.8 저장 부분만)

### 제외 (최종 결과물 단계로 이연 — 이번 계획서 범위 아님)
편차 원인 구분(6.5), 프로모션 효과성 평가(6.6), 대리점 그룹별 조회(6.7), 기준연월 이력 조회 UI(6.8 조회 부분), 프로모션 간/유형별 비교, 대리점등급 가중평균, 차기 설계안 제안, 결과 내보내기. `output/02_분석결과화면.html`·`output/03_이력_대시보드.html` 목업에는 이 기능들이 이미 시연되어 있지만, 이번 MVP 코드에는 구현하지 않는다.

### 완료 기준과 무관하게 처리해야 하는 엣지 케이스 (8절 중 MVP 해당분)
- 실적/기준 마스터 필수 컬럼 누락 → 업로드 즉시 오류 안내, 분석 진행 안 함
- 금액/비율 파싱 불가 값 → 해당 행 오류 표시, 전체 분석은 막지 않음
- 프로모션 기준 마스터 내 문턱값 구간 중복 → 업로드 단계 오류
- ~~실적 자료의 프로모션ID가 마스터에 없음 → 지원금액 0 처리 + "기준 미등록" 경고~~ **(삭제, 사용자 확인)**
- 제품군판매수량합계 원본 값과 재계산 값 불일치 → 재계산 값 우선 + 경고
- 전월매출 0 → 매출증감율 "N/A"
- 두 파일의 기준연월 불일치 → 경고 후 재확인 요청(자동 병합 금지)
- 연동형 트리거 미달 → 연동 대상 지원금액 0(DC 지원금액은 정상 계산)
- 같은 기준연월 재분석 → 기존 DuckDB 저장분 덮어쓰기

## 데이터 모델 (MVP에서 구현할 엔티티)

`02_PRD.md` 7절의 5개 엔티티 중 MVP 계산에 실제로 필요한 4개를 DuckDB 테이블로 둔다(STORE_AGM_BASELINE도 "구간별단가-대리점별상대" 산식이 MVP 범위인 6.3에 포함되므로 함께 구현).

| 테이블 | MVP에서의 역할 | 저장 방식 |
|---|---|---|
| `product_master` | 제품코드→타입·기준가 조회 (`sample03.csv` 시드) | 정적 시드 데이터, 앱 시작 시 1회 적재 |
| `promotion_master` | 업로드된 프로모션 기준 마스터를 그대로 적재해 매칭에 사용 | 업로드 시마다 갱신(전체 교체 또는 기준연월 단위 upsert) |
| `store_agm_baseline` | 대리점별상대 산식의 기준값(예: '25년 월평균 AGM 판매량) | 정적 시드 데이터 또는 업로드 |
| `sales_record` | 대리점×제품 실적 + 계산된 DC/프로모션 지원금액·영업이익율·매출증감율 | 분석 실행 시 기준연월 키로 upsert(덮어쓰기) |
| `applied_support` | 매칭된 프로모션별 지원금액 내역(0~N건/행) | `sales_record`와 함께 기준연월 키로 upsert |

## 구현 순서 (3일 집체 개발)

### Day 1 — 업로드·검증·데이터 계층
- Streamlit 앱 골격 생성(단일 페이지, 사이드바 또는 상단에 업로드 위젯 2개: 실적 파일 / 프로모션 기준 마스터)
- DuckDB 파일(`promotion_history.duckdb`) 초기화 스크립트: 5개 테이블 스키마 생성, `product_master`·`store_agm_baseline` 시드 적재
- openpyxl/pandas로 업로드 파싱: 필수 컬럼 검사, 금액(콤마)·비율(%) 문자열 → 숫자 변환, 오류 행 분리
- 업로드 단계 검증: 문턱값 구간 중복 검사, 두 파일 기준연월 일치 검사
- **Day 1 종료 기준**: 두 파일을 업로드하면 파싱된 DataFrame이 화면에 그대로 표시되고(계산 전), 누락 컬럼·중복 구간·기준연월 불일치를 정확히 잡아낸다.

### Day 2 — 워크북 인입 완성 · DB 연결 · UI 교체 **(수정, 사용자 확인 — 워크북 실물 확인 후 재정의)**
원래는 "프로모션 기준 마스터 업로드 + 산식 매칭 엔진"이었으나, 실제 월 마감 워크북(`sample04.xlsx`류)에는 DC·프로모션 지원금액이 이미 대리점 단위로 계산되어 있어(매칭·계산이 아니라 배분이 핵심) `app/workbook_ingest.py`로 방향을 바꿨다(Day 1 완료 후 반영, 위 참고). Day 2는 이미 만들어진 `workbook_ingest.py`를 완성하고 앱에 연결한다.

- **제품군 합산 판정**: `build_sales_like_table` 결과에 `제품군판매수량합계`(대리점×기준연월×제품군 판매수량 합)를 추가한다. sales_record 테이블에 이미 있는 컬럼인데 워크북 인입 결과에는 빠져 있었다.
- **지원유형별 내역 분리**: 현재는 DC 지원금액·프로모션 지원금액이 합산된 값만 나온다. `applied_support`에 채울 수 있도록 지원유형별(성과판촉DC/성장DC/10+1_GB/10+1_AGM/매출볼륨DC/대형할인) 개별 금액도 함께 반환하도록 `workbook_ingest.py`를 확장한다.
- **DB 연결**: `db.replace_period_data()`로 `build_sales_like_table` 결과(sales_record 모양 + applied_support 모양)를 기준연월 키로 저장한다. 컬럼명이 DDL과 정확히 일치하는지 맞춘다.
- **Streamlit UI 교체**: Day 1에서 만든 "실적 파일 + 프로모션 기준 마스터" 2파일 업로드 대신, 실제 워크북(총괄표·백데이터·프로모션·대형 시트 포함) 1개를 업로드받아 `workbook_ingest`로 처리하고 결과 표를 보여준다. Day 1의 `schema.py`/`validation.py`/`parsing.py` 기반 2파일 경로는 코드는 남겨두되(향후 팀 표준 양식이 바뀔 경우 대비) 화면에서 기본 경로로 쓰지 않는다.
- **Day 2 종료 기준**: `sample04.xlsx`를 업로드하면 (대리점, 제품) 단위 결과 표(제품군판매수량합계 포함)가 화면에 표시되고, "저장" 시 DuckDB에 기준연월 키로 남으며, 같은 기준연월을 다시 저장하면 정상적으로 덮어써진다.

### Day 3 — 지표 표시 다듬기 · QA **(수정, 사용자 확인 — DB 저장은 Day 2에서 이미 완료)**
DuckDB 저장 연결은 워크북 인입과 한 묶음이라 Day 2에서 먼저 끝냈다(`replace_period_data` 연결, 재분석 시 덮어쓰기 확인 메시지까지 포함). Day 3는 남은 두 가지에 집중한다.
- 결과 표 다듬기: 현재는 `st.dataframe`에 원본 컬럼명을 그대로 뿌리기만 한다. 금액(₩)·비율(%) 포맷, KPI 요약(대리점 수, 평균 영업이익율, DC/프로모션/총 지원금액 합계)을 추가해 6.4절이 요구하는 "지표를 나란히, 한눈에" 보여주는 화면에 가깝게 만든다(6.4) — 참고: `output/02_분석결과화면.html`의 KPI 카드·결과 표 UI. 편차 비교·그룹 조회 등 최종 결과물 섹션은 제외.
- QA: 9절 성공 지표 중 MVP 해당분 검증(아래 완료 기준 참고, 워크북 인입 구조에 맞게 재정의됨) + 버퍼 시간

## 화면 구성 메모
- MVP는 단일 화면(업로드 → 결과 표 한 페이지 흐름)으로 충분하다. `output/01_실적업로드.html`의 업로드 UI, `output/02_분석결과화면.html`의 KPI 카드·결과 표 UI를 Streamlit 컴포넌트로 재구현하되, 두 파일 모두에 있는 편차 원인 구분·효과성 평가·대리점 그룹별 조회·기준연월 드롭다운(조회 UI)은 MVP 화면에 넣지 않는다.
- `output/03_이력_대시보드.html`은 최종 결과물 단계 화면이므로 이번 계획서 범위에서 참고하지 않는다.
- design.md 토큰(색상·타이포·간격)은 Streamlit 테마(`.streamlit/config.toml`)와 커스텀 CSS(`st.markdown(<style>)`)로 최대한 반영하되, Streamlit 위젯 자체의 제약상 100% 재현은 어려울 수 있다는 점을 감안한다.
